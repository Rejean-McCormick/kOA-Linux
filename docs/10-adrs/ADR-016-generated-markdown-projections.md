# ADR-016 — Generated Markdown Projections

**ADR ID:** `ADR-016`  
**Status:** `accepted`  
**Decision class:** `major`  
**Decision owner:** `documentation-architecture`  
**Owner decision:** `DEC-DOC-GEN-001`  
**Created:** `2026-08-03`  
**Accepted:** `2026-08-03`  
**Effective:** `2026-08-03`  
**Supersedes:** Not applicable  
**Superseded by:** Not applicable

This ADR records the rationale, selected architecture, compatibility effects, migration, validation, and consequences of generated Markdown projections. The linked owner decision is the canonical authority for the outcome. The documentation registry owns the generation policy and projection registrations. The authority registry owns activation of a compatible documentation release.

## 1. Decision Summary

Canonical machine-readable registries and contracts own architectural facts.

Markdown can explain those facts, link to them, and display registered generated projections of them. Markdown does not become a second owner of values that already have a canonical structured owner.

The selected architecture uses two generated forms:

1. **embedded generated blocks** inside manually maintained explanatory Markdown; and
2. **fully generated files or packages** whose complete contents are produced by a registered generator.

Typical embedded blocks include document metadata, requirement statements, canonical component lists, artifact-class tables, profile matrices, and decision summaries.


A projection is deterministic, scoped, registered, reproducible, replaceable as one unit, and validated against its declared canonical inputs.

A semantic change begins at the canonical owner. The affected projections are then regenerated. Editing a generated occurrence does not change the underlying architecture and is rejected rather than reverse-imported.

The selected architecture also keeps generated AI contexts explicitly derivative. They can make applicable authority easier to consume, but they cannot create, broaden, narrow, reconcile, or supersede authority.

This decision does not govern:

- user-created documents;
- media derivatives produced by UCKK;

- build outputs outside the documentation architecture;
- manually written explanatory prose that does not reproduce canonical structured facts;

- examples that intentionally illustrate a format without claiming current canonical values.

Those objects use their own artifact, component, lifecycle, or documentation contracts.

### 2.3 Authority boundary

The decision applies when a projection is registered by:

```text
generated/document-index.json#/generation_policy
```

or by a generated-artifact pattern owned by that policy.

A generated occurrence is not authoritative merely because it appears in an active document.

Its authority is always inherited from the active canonical source set selected through the authority registry.

### 2.4 Integrity boundary

Ordinary manually maintained Markdown, including this ADR, does not carry documentation hash fields.

Integrity metadata for a generated artifact belongs to the registered generated-artifact manifest, documentation release manifest, or the generated artifact's own contract where applicable.

Currentness is proven through declared source identity, generator and renderer identity, clean regeneration, dependency validation, and release activation rather than by treating explanatory prose as an integrity ledger.

## 4. Context and Problem

### 4.1 Duplicate truth in Markdown

Architecture documentation often repeats structured facts in human-readable form:

- component identifiers;
- profile membership;
- release channels;
- requirement statements;
- lock meanings;
- decision status;
- artifact classes;
- interface catalogs;
- compatibility matrices;
- test coverage;

When each Markdown occurrence is edited manually, several problems appear:

- one value changes in the registry but not in prose;
- a list contains an obsolete identifier;
- requirement wording differs across documents;
- a table silently broadens scope;
- one profile matrix includes a component that the profile contract excludes;
- a generated context omits a prohibition;
- a copied statement loses its owner or source decision;
- maintainers cannot determine which occurrence is authoritative.

The problem is not that Markdown exists. The problem is duplicated manual ownership.

### 4.2 Human-readable documentation remains necessary

Machine-readable registries alone are insufficient for many tasks.

Readers need:

- explanation;
- rationale;
- procedures;
- failure behavior;
- examples;
- navigational tables;
- scoped summaries;
- implementation context;
- conformance views.

The architecture therefore needs a safe way to make canonical structured data visible without promoting every visible copy into a new source of truth.

### 4.3 Generated AI contexts create additional risk

AI agents benefit from smaller task-specific context packages.

A context package can include:

- applicable decisions;
- requirements;
- locks;
- component boundaries;
- profile behavior;
- prohibited assumptions;
- read order;
- output constraints.

Without a strict projection model, a context package can become a hidden parallel corpus. It can remain stale, omit an active restriction, mix profile scopes, include rejected decisions, or be edited manually until it no longer reflects active authority.

The problem therefore includes both Markdown projection and machine-consumable generated context.

### 4.4 Why a global decision is required

Generation affects:

- canonical ownership;
- requirement identity;
- decision closure;
- document activation;
- change impact;
- validation;
- AI behavior;
- migration;
- conformance claims;
- historical integrity.

Local generator conventions cannot resolve these effects consistently.

A global owner decision is required to determine:

- which facts can be projected;
- which source remains authoritative;
- how projection scope is declared;
- how deterministic generation is validated;
- how stale or modified output is handled;
- how AI context authority is constrained;
- how generation participates in activation and rollback.

### 4.5 Existing architectural constraints

The decision must preserve:

- one canonical owner per fact;
- registry-first structured authority;
- generated requirement statements;
- stable identifiers;
- accepted decision closure;
- strict scope classes;
- no inferred architecture;
- active English documentation;
- complete impact analysis;
- clean-repository validation;
- no parallel active corpus;
- no manual editing of fully generated output;
- historical retention without historical authority.

## 5. Decision Drivers

The decision drivers, in priority order, are:

1. **Single ownership.** A visible reproduction cannot become a second owner.
2. **Drift prevention.** Canonical changes and visible documentation need mechanical alignment.
3. **Exact normative projection.** Requirement identifiers, strengths, and statements need exact rendering.
4. **Scope safety.** Global, profile, overlay, component, artifact, and toolchain scope must not be mixed through presentation.
5. **Determinism.** Equal declared inputs need equivalent semantic output.
6. **Reviewability.** A reviewer needs to distinguish authored explanation from generated fact.
7. **Failure transparency.** Missing sources, conflicts, and missing decisions need explicit blocked results.
8. **AI safety.** Generated task contexts need to remain scoped and non-authoritative.
9. **Atomic activation.** An active documentation release cannot mix old canonical data with new projections.
10. **Migration practicality.** Existing manually duplicated tables and lists need a controlled path to generated form.
11. **Offline use.** Locally available active authority and projections need to remain usable without public services.
12. **Historical integrity.** Old projections need to remain interpretable as products of a prior authority release without being treated as current.

## 6. Considered Options

### 6.1 Option A — Registered deterministic projections

**Description**

Keep structured facts in canonical registries and contracts. Register every generated file or generated block pattern. Generate deterministic scoped projections. Validate source resolution, scope, output, manual-edit absence, and clean regeneration. Keep explanatory prose manually maintained.

**Advantages**

- preserves single ownership;
- prevents statement drift;
- supports exact requirement projection;
- supports human and AI views;
- makes generated regions identifiable;
- enables non-mutating check mode;
- supports impact-driven regeneration;
- makes stale content mechanically detectable;
- supports atomic documentation release activation.

**Costs**

- requires generator and renderer contracts;
- requires regeneration in semantic changes;
- increases validation complexity;
- requires migration of existing manual reproductions;
- requires reviewers to understand generated boundaries;
- requires stable source references and deterministic ordering.

**Constraint fit**

This option satisfies all linked documentation locks.

### 6.2 Option B — Manual Markdown copies with review discipline

**Description**

Allow authors to copy structured values into Markdown and rely on review checklists to keep them synchronized.

**Advantages**

- simple author workflow;
- no generator implementation;
- easy local edits;
- no generated markers.

**Costs**

- drift remains likely;
- requirement wording can diverge;
- profile and component tables can contradict registries;
- reviewers must compare many files manually;
- AI contexts can become stale parallel authority;
- changes cannot be validated reproducibly.

**Reason rejected**

Review discipline is insufficient for repeated canonical data across a large authority graph.

### 6.3 Option C — Generate all Markdown completely

**Description**

Make every active Markdown file fully generated from structured data.

**Advantages**

- strong mechanical consistency;
- no mixed authoring model;
- easy full-file regeneration;
- deterministic layouts.

**Costs**

- structured registries would need to own long explanations, rationale, procedures, and examples;
- prose quality and maintainability would decline;
- small explanatory edits would require structured source changes;
- documents would become renderer-specific;
- human-authored architectural explanation would be constrained unnecessarily.

**Reason rejected**

Not every useful documentation sentence is a structured canonical fact. A hybrid model is more precise.

### 6.4 Option D — Treat generated output as a second canonical layer

**Description**

Allow generated Markdown and context packages to become authoritative after validation, even when they duplicate source registries.

**Advantages**

- consumers can use one rendered artifact without resolving sources;
- archive snapshots are self-contained;
- some tooling becomes simpler.

**Costs**

- creates multiple owners;
- requires conflict rules between source and output;
- permits generated omissions to change authority;
- makes reverse synchronization necessary;
- weakens source-of-truth reasoning;
- turns renderer bugs into architectural changes.

**Reason rejected**

Validation does not transform a projection into the owner of the facts it displays.

### 6.5 Option E — AI-generated summaries without registered projection contracts

**Description**

Allow an AI agent to summarize active sources for each task and rely on prompt instructions to preserve scope and authority.

**Advantages**

- flexible;
- no generator registry;
- task-specific output;
- low initial tooling cost.

**Costs**

- non-deterministic selection and wording;
- omitted restrictions;
- scope drift;
- missing decision inference;
- no stable artifact identity;
- difficult review and reproduction;
- context packages can silently disagree.

**Reason rejected**

AI can assist generator development or explanatory drafting, but active projections need deterministic registered contracts.

## 7. Decision

### 7.1 Selected option

`Registered deterministic projections`

### 7.2 Projection principle

A generated projection:

- identifies the canonical data it displays;
- identifies its intended scope and output role;
- preserves canonical identifiers;
- preserves lifecycle and applicability;
- preserves requirement strength and statement;
- follows deterministic selection and ordering;
- contains no new architectural decision;
- has no independent ownership;
- can be discarded and rebuilt from canonical sources;
- participates in documentation release validation.

### 7.3 Generated forms

The architecture recognizes:

| Form | Ownership and edit model |
| --- | --- |
| Embedded generated block | The surrounding document is manually maintained; the marked block is generator-owned and replaced as one unit. |
| Fully generated Markdown file | The entire file is generator-owned; direct editing is invalid. |
| Fully generated structured package | The complete JSON or equivalent package is generator-owned and validated against its package contract. |
| Generated report | The report is a derived result bound to declared inputs and target scope. |
| Generated manifest | The manifest records a release, projection, or context artifact set under its own contract. |

A file can contain several generated blocks when each block has one registered projection identity or pattern.

Nested overlapping generated blocks are not permitted.

### 7.4 Projection classes

The selected model supports these representative classes:

| Projection class | Purpose | Canonical owner | Typical generated form |
| --- | --- | --- | --- |
| document metadata | Registered document identity, class, lifecycle, language, scope, dependencies, and canonical references. | Documentation registry and referenced canonical registries. | Generated metadata envelope in an otherwise maintained document. |
| requirements block | Requirement identifiers, strengths, and exact statements selected for one normative document. | Requirements registry plus document projection metadata. | Generated block embedded in normative Markdown. |
| lock summary | Applicable alignment-lock identifiers, meanings, assertion status, and owners. | Locks registry and validation results. | Generated block or generated conformance report. |
| decision index | Applicable accepted decisions, versions, scope, and lifecycle. | Decisions registry and traceability registry. | Generated table, index, or scoped context package. |
| ADR index | Accepted ADR identity, path, status, owner decision, scope, and succession. | ADR registry. | Generated catalog or navigation page. |
| component catalog | Registered components, responsibilities, contracts, profiles, and ownership summaries. | Components registry and component-contract index. | Generated catalog, table, or profile projection. |
| profile matrix | Profile membership, overlays, capabilities, components, artifacts, and constraints. | Profile index and profile contracts. | Generated matrix or profile summary. |
| artifact-class matrix | Artifact classes, channels, signers, compatibility, activation, rollback, and evidence. | Artifact-class and release-channel registries. | Generated lifecycle table or release matrix. |
| traceability matrix | Typed relationships among decisions, requirements, locks, documents, tests, evidence, components, profiles, and artifacts. | Traceability registry. | Generated report or filtered matrix. |
| impact report | Direct and transitive affected objects and their explicit dispositions. | Canonical dependency graph and accepted change inputs. | Generated change-control artifact. |
| AI context package | Scoped read order, applicable authority, excluded scope, prohibited assumptions, and task context. | AI-context registry plus applicable canonical registries. | Fully generated package with no independent authority. |
| conformance report | Applicable requirement versions, test results, evidence, exceptions, and blocked states. | Requirements, test, evidence, exception, and traceability registries. | Generated report bound to one declared target scope. |

The table is explanatory. The documentation registry owns active projection identifiers and patterns.

### 7.5 Projection descriptor

A registered projection descriptor normally identifies:

- projection identity;
- target path or embedded target selector;
- target document identity where applicable;
- projection class;
- canonical source references;
- source selection rules;
- included scope;
- excluded scope;
- generator identity and version;
- renderer identity and version;
- output schema or block format;
- deterministic ordering;
- normalization;
- conflict behavior;
- missing-source behavior;
- output access classification;
- replacement behavior;
- check-mode behavior;
- lifecycle;
- validation tests;
- owner.

A descriptor can reference shared renderer contracts rather than duplicate formatting rules.

### 7.6 Canonical-source rule

A generator reads only active canonical objects selected through the current authority set and its declared source references.

It does not scan arbitrary prose to discover architectural facts.

It can use explanatory prose only when the projection contract explicitly classifies that prose as the source object, such as a generated navigation excerpt. Such use does not convert the prose into a structured owner of unrelated facts.

### 7.7 No semantic inference

A generator does not:

- select a missing owner;
- create a default;
- reconcile conflicting accepted sources;
- promote profile behavior to global;
- infer component ownership from implementation;
- infer release compatibility;
- add a requirement;
- change normative strength;
- repair a missing decision;
- select an exception;
- choose an external provider;
- omit a restriction because it is inconvenient for the target format.

A blocked result is preferred over a plausible output.

### 7.8 Scope selection

Projection scope is explicit.

A projection can target:

- global authority;
- named profiles;
- named profile overlays;
- named components;
- named artifact classes;
- named toolchains;
- migration-only content;
- review-only historical context.

The output identifies included and excluded scope when omission could be misinterpreted.

A context package for one component and profile cannot be reused as a global architecture context.

### 7.9 Determinism

Generation uses declared:

- source set;
- source versions;
- selection;
- normalization;
- ordering;
- renderer;
- configuration;
- language;
- line-ending and encoding policy;
- environment constraints.

Exact byte identity is desirable for stable text output, but the conformance requirement is deterministic semantic output under the registered renderer contract. Platform-specific timestamps, absolute paths, random identifiers, locale-sensitive sorting, and uncontrolled environment values are excluded.

Where a generated artifact contract records content fingerprints, those values are produced by the generator or release tooling and are not manually maintained in ordinary Markdown.

### 7.10 Generated-block boundaries

An embedded block has:

- one recognizable begin marker;
- one recognizable end marker;
- a registered projection identity or source declaration;
- content generated as a single replacement unit.

The marker format is owned by the generation policy.

The surrounding author can move or remove a block only through a registered document or projection change. The author does not edit the body.

### 7.11 Requirement projection

A normative Markdown document selects requirement identifiers through generated metadata or another registered projection field.

The requirement block renders the exact canonical:

- identifier;
- strength;
- statement.

Explanatory prose outside the block does not create additional normative requirements.

Metadata requirement identifiers and rendered requirement identifiers remain identical as sets and ordering where ordering is owned.

### 7.12 Generated metadata

Generated document metadata can project:

- document identity;
- class;
- lifecycle;
- language;
- layer;
- scope;
- canonical references;
- decisions;
- requirements;
- locks;
- exceptions;
- dependencies;
- tags.

The metadata block is not a second owner of those values. It is a document-local projection used for validation and navigation.

### 7.13 AI context packages

An AI context package is a scoped derived artifact.

It identifies:

- package identity;
- target operation;
- included profiles, overlays, components, artifacts, and toolchains;
- excluded scope;
- active decisions;
- requirements;
- locks;
- exceptions;
- canonical references;
- read order;
- prohibited assumptions;
- lifecycle and freshness;
- generator and renderer identity;
- validation result.

It excludes:

- proposed decisions from implementation authority;
- superseded authority except when historical review is requested;
- secrets;
- unrestricted private evidence;
- protected subject content not required by the task;
- arbitrary conversation history as architecture authority.

An AI agent remains responsible for respecting the package scope and blocked results.

### 7.14 Generated labels

A renderer can add:

- headings;
- table columns;
- grouping labels;
- navigation;
- explanatory captions;
- display-only row numbers;
- status icons represented accessibly;
- empty-state messages.

These additions remain non-normative and cannot change canonical meaning.

A display-only identifier is clearly distinguished from canonical identifiers.

### 7.15 No reverse import

A manual change to generated output is never interpreted as an intended canonical change.

The repair path is:

1. identify the expected canonical owner;
2. update the owner or projection contract through accepted change control;
3. regenerate;
4. validate.

This rule prevents accidental authority transfer from projection to output.

## 8. Generation Lifecycle

### 8.1 Lifecycle states

A generated artifact can be:

| State | Meaning |
| --- | --- |
| `absent` | A registered required projection does not exist. |
| `generated` | Output was produced but has not completed validation. |
| `validated` | Output passes its schema, source, scope, determinism, and projection checks. |
| `active` | The validated output belongs to the active documentation authority release as a derived artifact. |
| `stale` | A relevant source, decision, descriptor, generator, renderer, or configuration changed. |
| `invalid` | The output is modified, incomplete, non-deterministic, unsafe, or inconsistent with canonical inputs. |
| `superseded` | A newer registered projection replaces it. |
| `archived` | The artifact is retained as historical output of a prior authority release. |

A stale or archived projection can be read for history but cannot support current implementation or conformance unless its historical release is explicitly the subject of review.

### 8.2 Generation sequence

A standard generation run:

1. resolves the active authority set;
2. validates source schemas;
3. verifies decision closure;
4. resolves projection descriptors;
5. resolves all canonical source references;
6. computes target scope;
7. rejects conflicts and missing authority;
8. normalizes declared inputs;
9. orders collections deterministically;
10. renders into memory or a temporary path;
11. validates the candidate output;
12. compares check-mode output with repository output;
13. replaces the target atomically during write mode;
14. updates the generated-artifact or documentation release manifest where applicable;
15. runs complete documentation validation.

Partial output is not written to the final target.

### 8.3 Non-mutating check mode

Every generator used as an activation gate supports a non-mutating check operation.

Check mode:

- computes expected output;
- reports absent, unexpected, stale, modified, or invalid artifacts;
- does not alter the repository;
- produces a machine-readable result;
- identifies the projection and source causing each mismatch.

Check mode cannot repair the repository silently.

### 8.4 Change-driven invalidation

When a canonical object changes, impact analysis identifies dependent projections.

Each affected projection receives a disposition such as:

- regenerated;
- validated unchanged;
- superseded;
- retired;
- not applicable.

The documentation authority release remains inactive until every required projection has a complete disposition and passing validation.

### 8.5 Generator change

A generator change identifies:

- generator version;
- affected projection classes;
- semantic versus formatting effect;
- migration;
- expected output changes;
- tests;
- compatibility;
- regeneration set.

A generator bug fix cannot alter canonical meaning. When an earlier renderer omitted or changed meaning, repaired outputs are treated as corrections to the projection and are reviewed for affected implementation or conformance reliance.

### 8.6 Renderer change

Renderer versioning distinguishes:

- formatting-only compatible changes;
- compatible metadata or navigation additions;
- incompatible output structure or interpretation changes.

An incompatible renderer change includes migration for consumers and generated contexts.

### 8.7 Source relocation

When a canonical source moves:

1. the canonical owner approves the move;
2. path and redirect rules are updated;
3. impact analysis finds all projection descriptors and contexts;
4. source references are migrated;
5. projections are regenerated;
6. historical manifests preserve the earlier source relationship;
7. the new authority release activates last.

A generator does not search for a similarly named replacement.

## 9. Canonical Ownership and Edit Boundaries

### 9.1 Canonical owner

The canonical owner is the structured registry, contract, schema, or accepted source object registered for the fact.

Examples include:

- requirements registry for normative statements;
- decisions registry for owner decisions;
- components registry for component inventory;
- profile contracts for profile membership and values;
- artifact-class registry for artifact classes;
- documentation registry for document and projection policy;
- AI-context registry for context package definitions;
- traceability registry for relationship graphs.

### 9.2 Markdown owner

Manually maintained Markdown owns explanation, rationale, procedures, consequences, and non-normative examples where the documentation architecture assigns it that role.

It references canonical facts rather than redefining them.

### 9.3 Generator owner

A generator owner maintains the transformation contract and implementation.

The owner does not own the architectural values supplied as input.

A generator owner cannot change output meaning by changing code without the applicable semantic decision and impact process.

### 9.4 Author edit boundary

An author can edit:

- explanatory paragraphs;
- rationale;
- procedures;
- examples;
- links;
- manually maintained navigation not reproducing canonical lists;
- projection placement through the registered change workflow.

An author does not edit:

- generated block bodies;
- fully generated files;
- generated context packages;
- generated manifests;
- generated conformance matrices.

### 9.5 Validator boundary

A validator determines whether:

- the projection is registered;
- sources resolve;
- scope is correct;
- content matches a clean generation;
- generated boundaries are intact;
- output contains no forbidden semantic additions;
- active release consistency is complete.

A passing validator does not turn an architecturally incorrect canonical source into a correct decision.

## 10. Security, Privacy, Rights, and AI Effects

### 10.1 Sensitive-source filtering

A projection descriptor identifies its output access class.

A public or broadly distributed projection excludes:

- secrets;
- private keys;
- credentials;
- protected personal data;
- private consent evidence;
- private cultural-rights evidence;
- unrestricted diagnostics;
- private incident evidence;
- protected source content;
- confidential implementation details not required by the projection.

Filtering is based on canonical policy and explicit source selection, not on renderer guesses.

### 10.2 Disclosure and cultural rights

A generated catalog, context package, or report can reveal facts even when it excludes payload content.

Projection design therefore evaluates:

- existence disclosure;
- metadata visibility;
- audience;
- purpose;
- aggregation risk;
- cultural-rights policy;
- consent;
- retention;
- export;
- publication boundary.

A generated index is not exempt from disclosure controls because it contains only metadata.

### 10.3 AI contexts

AI contexts are minimized for their declared task.

They preserve applicable prohibitions and authority boundaries.

They do not include private evidence merely to improve model accuracy.

They do not treat model-generated summaries as canonical replacements for source registries.

### 10.4 Prompt and output injection resistance

Canonical values are represented as data under a registered renderer.

Untrusted source content is not executed as generator instructions.

Generated contexts distinguish:

- authoritative fields;
- explanatory source text;
- quoted user or historical content;
- prohibited assumptions;
- task instructions.

A protected subject's content cannot insert a new architecture instruction into an AI context.

### 10.5 Integrity and release evidence

Generated artifacts used in a documentation or authority release can be covered by generated-artifact manifests and release evidence.

Integrity values are generated and verified under those artifact contracts.

They are not typed manually into explanatory documents and do not become semantic owners.

## 11. Offline and Operational Effects

### 11.1 Local generation

Generation can run using the complete locally available active authority set.

It does not require public DNS, external AI, external voice, or public time services.

A generator can require locally verified toolchain and authority-release inputs.

### 11.2 Offline context use

A locally verified context package can support offline work within its declared scope and authority release.

The package exposes its release identity and freshness.

A stale package does not silently become current because connectivity is absent.

### 11.3 Resource behavior

Large matrices and context packages use bounded resource envelopes.

Generation can:

- stream source data;
- use deterministic paging;
- cap output size by registered scope;
- split artifacts through registered sharding rules;
- queue optional reports;
- preserve interactive documentation work.

Resource pressure cannot justify omission of required restrictions or silent truncation.

### 11.4 Health and readiness

Documentation generation health distinguishes:

- source readiness;
- decision-closure readiness;
- generator readiness;
- renderer readiness;
- output validation;
- projection staleness;
- manifest readiness;
- authority activation readiness.

A generator process being alive does not mean projections are current.

### 11.5 Backup and restore

Canonical sources and projection descriptors are the essential restoration inputs.

Generated output can be restored from backup for historical continuity, but current output is regenerated and validated against the restored active authority.

A backup of generated files alone is insufficient to reconstruct canonical authority.

## 12. Compatibility and Lifecycle

### 12.1 Compatibility class

`breaking`

The decision is breaking relative to a documentation model in which repeated Markdown values can be edited manually and interpreted as current authority.

It is compatible with manually maintained explanatory prose and with historical Markdown retained as non-authoritative source material.

### 12.2 Consumer compatibility

Consumers fall into these classes:

| Consumer | Compatibility requirement |
| --- | --- |

| Conformance tool | Resolves exact requirement, decision, lock, test, and evidence identifiers from canonical sources. |
| Migration tool | Preserves source-to-projection lineage and does not reverse-import output. |
| Archive reader | Can identify the authority release that produced a historical projection. |

### 12.3 Documentation lifecycle

Generated projections advance with the documentation authority release.

A projection can be activated only as part of a compatible set containing:

- canonical source versions;
- accepted decisions;
- requirements;
- locks;
- projection descriptors;
- generators and renderers;
- generated output;
- validation results;
- applicable contexts and manifests.

### 12.4 Product release channels

This decision does not merge generated documentation with the system, services, governance, or knowledge product release channels.

A generated document can describe those channels, but its activation belongs to the documentation authority lifecycle.

Generated product manifests or evidence artifacts remain governed by their own artifact contracts.

## 14. Rollback and Forward Repair

### 14.1 Rollback triggers

Rollback or activation rejection is required when:

- generated output differs from clean generation;
- a generated file contains manual edits;
- a generated block is malformed;
- source references do not resolve;
- scope selection is wrong;
- a requirement statement differs from the registry;
- a generated context includes inactive authority;
- a required restriction is omitted;
- protected data is exposed;
- non-deterministic semantic output appears;
- a projection descriptor is missing;
- the documentation release mixes incompatible source and output versions.

### 14.2 Rollback unit

The rollback unit is the complete documentation authority set containing:

- active canonical registries and contracts;
- documentation generation policy;
- projection descriptors;
- generator and renderer versions;
- generated outputs;
- AI contexts;
- locks;
- traceability;
- validation results;
- release manifest.

A single edited Markdown block is not a complete rollback unit.

### 14.3 Rollback procedure

1. Stop candidate documentation activation.
2. Restore the previous validated authority and projection set.
3. preserve the failed candidate and diagnostics;
4. verify that historical and current paths remain distinguishable;
5. rerun generated-content and full documentation validation;
6. reactivate only the previous complete set.

### 14.4 Forward repair

Forward repair is preferred when canonical authority has validly changed and only projection generation is defective.

Repair can:

- correct source mapping;
- correct filtering;
- correct deterministic ordering;
- repair renderer escaping;
- restore generated boundaries;
- remove exposed sensitive fields;
- regenerate all affected outputs;
- update consumer compatibility;
- issue a new validated documentation release.

The repair does not revert a valid canonical semantic change merely to preserve an obsolete visible table.

### 14.5 Last known valid state

The last known valid state is the documentation authority release whose canonical sources, projection descriptors, generated outputs, contexts, locks, and validation results form one compatible set.

The authority registry owns that release identity.

## 15. Failure States and Safe Degradation

| Failure state | Required response |
| --- | --- |
| Canonical source is absent | Generation stops, the candidate projection remains unavailable, and any prior output is classified as historical or stale rather than current. |
| Canonical source is invalid | Dependent generation stops; invalid input is not normalized into an apparently valid projection. |
| Canonical references do not resolve | The projection is blocked and reports the exact missing path or identifier. |
| Required owner decision is missing | Generation returns a blocked authority result and does not choose a default. |
| Canonical sources conflict | Generation fails unless an accepted authority rule already resolves the conflict. |
| Projection contract omits an applicable source | Impact and completeness validation fail before activation. |
| Generator is unavailable | No new projection is activated; the previous validated output can remain readable only under its recorded authority release. |
| Generator produces non-deterministic semantic output | Validation fails and activation is blocked until ordering, normalization, environment, or renderer behavior is repaired. |
| Generated block was manually edited | The edit is rejected, the block is regenerated from canonical data, and no reverse import occurs. |
| Fully generated file was manually edited | The file is invalid and is replaced only by a clean generator run. |
| Projection is stale | It remains excluded from current implementation, conformance, and release contexts until regenerated and validated. |
| Output contains a new architectural fact | Validation fails because the generator exceeded projection authority. |
| Output changes requirement strength or scope | Validation fails and the canonical requirement remains unchanged. |
| Output hides a required restriction | The projection is rejected even when the visible result is syntactically valid. |
| Output exposes protected or secret material | Publication stops, the artifact is quarantined or removed from the candidate release, and incident handling begins where required. |
| AI context includes an inapplicable decision | The package is rejected and rebuilt using exact scope selection. |
| AI context omits a required prohibition | The package cannot support implementation-affecting work. |
| Repository is incomplete or dirty for validation | The result is not eligible for activation. |
| Canonical path moved without updating the projection contract | Generation fails on the old reference until redirect, replacement, and impact changes are accepted. |
| Renderer change alters interpretation | The change is handled as a semantic renderer version transition with impact review and regeneration. |

Safe degradation preserves the last known valid authority set for reading where appropriate, but it does not present stale output as current and does not permit semantic edits to generated occurrences.

## 21. Implementation Guidance

This section is explanatory.

A practical generator implementation can use this workflow:

1. Read the active authority release.
2. Read one registered projection descriptor.
3. Resolve every repository-relative source and pointer.
4. Validate source schemas.
5. Select the exact target scope.
6. Reject inactive or conflicting authority.
7. Convert source objects into an internal typed projection model.
8. Sort using explicit stable keys.
9. Render using a versioned renderer.
10. Validate the candidate in memory.
11. In check mode, compare and report without writing.
12. In write mode, replace the target atomically.
13. Run generated-boundary and full-document validation.
14. Record impact and release evidence.

Useful design practices include:

- keep source selection separate from presentation;
- use typed intermediate objects;
- make empty-state behavior explicit;
- escape untrusted text for the target format;
- avoid host paths and environment-dependent ordering;
- keep timestamps out of stable output unless they are canonical data;
- use one block identity per generated region;
- make generated comments machine-readable and human-recognizable;
- preserve canonical identifiers in visible output;
- test both permitted and prohibited scope selection;
- test removal of a source object;
- test missing decisions and conflicting sources;
- test that manual edits are overwritten only by an explicit write-mode regeneration;
- keep check mode the default for validation.
