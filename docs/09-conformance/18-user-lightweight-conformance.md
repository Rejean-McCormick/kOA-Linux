# User Lightweight Conformance

## 1. Purpose

This document defines how a deployment demonstrates conformance to the `user_lightweight` profile.

The profile is a complete primary deployment form for a single-user or small local installation with a bounded hardware and resource envelope. Conformance demonstrates that the selected global baseline, profile-owned capabilities, component boundaries, operational behavior, security controls, lifecycle controls, tests, and evidence agree for one exact tested system.

The profile is lightweight by controlled scope and resource behavior. It is not conformant merely because an installation is small, uses few services, runs on one machine, or omits tests.

## 2. Scope

This document applies to:

- the active `user_lightweight` profile contract;
- the global requirements applicable to that profile;
- profile-specific hardware and resource assertions;
- component and capability membership;
- local navigation and accessibility;
- deterministic local kOA Mediatheque behavior;
- optional external artificial-intelligence surfaces;
- absence of SenTient;
- optional container use;
- absence of a Kubernetes endpoint requirement;
- desktop and appliance-overlay separation;
- data ownership and permitted shared database topology;
- health, readiness, degradation, observability, backup, restore, portability, and incident response;
- artifact verification, release compatibility, update, rollback, and forward repair;
- profile test matrices, evidence, exceptions, and claims;
- explicit composition of `high_assurance`, `sovereign_offline`, or `appliance_shell`.

This document does not:

- define the profile's canonical numeric hardware values;
- make recommended hardware values mandatory;
- make every optional component or external integration part of the profile;
- add sovereign, high-assurance, appliance, developer, build-farm, or control-plane obligations to the base profile;
- prescribe one desktop, container runtime, database packaging, metrics backend, backup product, or service manager;
- treat a running installation as proof of conformance;
- replace the profile contract, test catalog, evidence registry, or profile claim artifact.

## 4. Model and Responsibilities

### 4.1 Conformance subject

A claim applies to one exact subject:

- system or installation identity;
- profile identity and version;
- authority-set version;
- component versions;
- artifact versions and release channels;
- effective overlays;
- hardware and operating environment;
- test environment;
- claim time.

A claim cannot be transferred to a materially different host, profile composition, component set, artifact set, or authority version without re-evaluation.

### 4.2 Claim dimensions

A complete claim covers:

| Dimension | Conformance question |
| --- | --- |
| Profile identity | Is the active primary profile exactly `user_lightweight`? |
| Global baseline | Do all globally applicable requirements pass? |
| Profile assertions | Do all profile-owned requirements and exclusions pass? |
| Hardware | Does the host satisfy every minimum profile field and required operating mechanism? |
| Resources | Are jobs, queues, retries, processes, memory, input-output, and concurrency bounded? |
| Components | Are required components present and prohibited components absent? |
| Data | Are logical ownership and component database identities preserved? |
| Artificial intelligence | Is the native baseline deterministic and are external surfaces optional and controlled? |
| Experience | Does local navigation remain available independently from optional external voice? |
| Runtime topology | Are containers optional and Kubernetes absent as a baseline dependency? |
| Lifecycle | Are artifacts verified, compatible, recoverable, and correctly activated? |
| Operations | Are health, readiness, degradation, backup, restore, observability, and incidents validated? |
| Evidence | Do applicable tests produce complete current evidence? |

### 4.3 Base profile and overlays

The base claim contains only the behavior selected by `user_lightweight`.

An overlay claim is additional:

`text
user_lightweight
 + optional compatible overlay
 = composed profile claim
`

The base claim does not inherit overlay requirements by naming similarity, deployment preference, or implementation choice.

An overlay can strengthen the composed claim. It cannot weaken a global prohibition or a base-profile requirement.

### 4.4 Hardware evidence

Hardware evidence identifies the tested processor, memory, storage, graphics capability, compressed-memory swap state, and heavy-job admission behavior.

The test resolves exact minimum and recommended values from the active profile contract. The conformance report distinguishes:

- mandatory minimum result;
- recommended-envelope result;
- measured resource behavior;
- unsupported or unresolved hardware fields.

The Markdown document does not reproduce the numeric envelope.

### 4.5 Resource behavior

The Resource Governor provides the baseline resource-authority relationship for this profile.

Evidence can include:

- resource-envelope validation;
- one-heavy-job admission tests;
- queue and retry bounds;
- memory-pressure behavior;
- compressed-memory swap state;
- input-output throttling;
- process limits;
- safe rejection or deferral;
- recovery after resource pressure.

A small host does not justify unbounded work.

### 4.6 Capability and exclusion model

The claim distinguishes:

- required capability;
- optional capability;
- prohibited capability;
- externally supplied capability;
- overlay-contributed capability;
- unavailable capability with safe degradation.

SenTient is excluded from this profile. External voice, Suno, Gamma, and other approved external surfaces remain optional and cannot become prerequisites for local core operation.

### 4.7 Local deterministic core

The local core includes only capabilities selected by the profile and their applicable component contracts.

Relevant conformance properties include:

- deterministic local navigation;
- deterministic native kOA Mediatheque processing;
- no native artificial-intelligence authority;
- local component data ownership;
- bounded resource use;
- health and readiness;
- recovery and portability;
- no silent external substitute.

### 4.8 Data topology

The profile can use a shared PostgreSQL process where the profile contract permits it.

Conformance remains based on logical separation:

- separate database or schema per component;
- separate database identity per component;
- no cross-component direct writes;
- explicit APIs, commands, events, gateways, or artifacts for cross-component interaction;
- backup and restore preserving ownership.

Physical process sharing does not create shared data authority.

### 4.9 Claim outcomes

This document uses the following explanatory outcomes:

| Outcome | Meaning |
| --- | --- |
| Conformant | Every mandatory applicable check passed and required evidence is valid |
| Nonconformant | At least one mandatory applicable check failed |
| Blocked | A required authority, reference, test, environment, or evidence item could not be resolved |
| Incomplete | The evaluated set does not yet support a complete claim |
| Not applicable | The canonical profile or composition excludes the requirement |
| Excepted | An active scoped exception controls the deviation and its compensating evidence |

Exact machine-readable outcome fields remain owned by the profile-claim contract.

### 4.10 Evidence package

A claim package identifies:

- profile and authority versions;
- system and hardware subject;
- effective overlays;
- applicable requirement inventory;
- lock results;
- component and artifact inventory;
- test matrix;
- test results;
- evidence references;
- exceptions;
- unresolved or blocked items;
- claim outcome;
- verifier identity and time.

The evidence package supports the claim. It does not alter the profile contract.

## 6. Procedures or State Transitions

### 6.1 Preparing the claim

Claim preparation:

1. identifies the tested installation;
2. resolves the active authority set;
3. resolves `user_lightweight` and its exact version;
4. resolves explicitly composed overlays;
5. inventories hardware, operating environment, components, artifacts, and release channels;
6. builds the applicable requirement, lock, test, and evidence matrix;
7. resolves active exceptions;
8. records the clean test context.

### 6.2 Validating the base profile

Base validation:

1. validates profile identity and primary classification;
2. validates all globally applicable requirements;
3. validates all base-profile requirements and exclusions;
4. validates hardware and resource behavior;
5. validates component and capability membership;
6. validates data ownership;
7. validates local navigation and deterministic local processing;
8. validates optional external surfaces and safe degradation;
9. validates runtime topology;
10. validates lifecycle, operations, security, and evidence.

### 6.3 Validating overlays

For each explicit overlay:

1. validate applicability to `user_lightweight`;
2. validate composition and precedence;
3. add the overlay requirement and lock set;
4. add or restrict components and capabilities;
5. add tests and evidence;
6. verify that no base or global prohibition is weakened;
7. record the overlay result separately;
8. calculate the composed-profile outcome.

### 6.4 Testing degraded operation

Degradation validation:

1. disconnect optional external services;
2. disable external voice;
3. remove optional container dependencies when the implementation permits;
4. constrain resources to declared operating conditions;
5. exercise queue and heavy-job admission;
6. verify local navigation and applicable core capability;
7. verify visible bounded degraded states;
8. verify that no silent substitute or authority escalation occurs.

### 6.5 Producing the claim

Claim production:

1. records every applicable requirement outcome;
2. links each mandatory result to tests and evidence;
3. records non-applicable and excepted relationships explicitly;
4. records unresolved and failed items;
5. calculates the profile and overlay outcomes without hiding mandatory gaps;
6. signs or records the claim according to the active evidence contract;
7. preserves the tested subject and authority versions;
8. publishes only the disclosure-approved claim view.

### 6.6 Revalidating

Revalidation occurs after a semantic change to:

- profile or overlay contracts;
- hardware or resource assertions;
- component membership;
- artificial-intelligence boundaries;
- data topology;
- runtime topology;
- artifact or release state;
- tests or evidence;
- exceptions;
- the tested installation.

Impact analysis determines which previous evidence remains reusable.

## 8. Cross-Component Interactions

### 8.1 Profile authority

The profile contract selects the applicable global and profile-specific behavior.

Conformance tools evaluate that selection. They do not add components, capabilities, overlays, hardware requirements, or exclusions.

### 8.2 Resource Governor

Resource Governor supplies evidence for bounded operation, heavy-job admission, queues, memory pressure, input-output, and process limits.

A resource result does not establish policy authorization, data ownership, or artifact compatibility.

### 8.3 Components and data stores

Each component proves its own required interfaces, data ownership, health, readiness, artifacts, and failure behavior.

A shared database process is infrastructure. Component contracts and database identities preserve logical authority.

### 8.4 External surfaces

External artificial-intelligence adapters and external voice remain separate integrations.

The profile claim evaluates user initiation, data transfer, provenance, acceptance, availability, and safe degradation without treating the external provider as a native component.

### 8.5 Lifecycle and release systems

Artifact verification and activating components establish exact artifact identity, trust, compatibility, activation, rollback, and forward repair.

A profile claim references those results for the tested installation and cannot generalize them to other artifact sets.

### 8.6 Test and evidence systems

The test catalog defines applicable tests and the evidence registry preserves results.

Conformance reporting cannot reinterpret a failed, blocked, stale, or out-of-scope result as passing evidence.

### Prohibited assumptions

- a low-cost or small machine is automatically conformant;
- recommended hardware is a mandatory minimum;
- one successful startup validates the profile;
- containers are required because a recipe uses them;
- Kubernetes is required because another profile permits it;
- the appliance shell is part of the base profile;
- high assurance or sovereign offline behavior is inherited automatically;
- SenTient is optional within `user_lightweight`;
- external voice is required for Ariane navigation;
- an unavailable external service can be replaced silently;
- native kOA Mediatheque includes automatic external artificial-intelligence classification or summarization;
- UCKK is required for local Mediatheque operation or owns local kOA media after publication;
- a shared database process permits shared component credentials;
- Resource Governor and Governance Policy Runtime are interchangeable;
- an operational installation proves data-boundary conformance;
- stale evidence supports a changed profile or artifact set;
- aggregate coverage hides a failed mandatory test;
- a profile exception applies outside its exact scope and validity;
- a profile claim can omit the tested authority and artifact versions.

## 11. Non-Normative Examples

> **Non-normative example:** This example illustrates minimum and recommended hardware.

A host can satisfy every mandatory profile-owned minimum while not meeting one recommended value. The base conformance result can pass while the recommendation status remains visible.

> **Non-normative example:** This example illustrates optional containers.

One implementation can run selected services in permitted containers while another uses native service isolation. Both can support the same profile claim when their component contracts, resource behavior, and boundaries pass.

> **Non-normative example:** This example illustrates local navigation.

External voice is disabled during testing. Keyboard, pointer, touch, menus, accessibility controls, deterministic commands, and local shortcuts remain available.

> **Non-normative example:** This example illustrates shared database infrastructure.

Several components can use one PostgreSQL process while retaining separate databases or schemas and separate identities. A direct write from one component into another component's authoritative tables fails the claim.

> **Non-normative example:** This example illustrates an overlay.

A `user_lightweight` installation with an explicitly compatible `appliance_shell` overlay has one base-profile result and one overlay-composition result. Appliance restrictions are not retroactively applied to every base-profile deployment.
