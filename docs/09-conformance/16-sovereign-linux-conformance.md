# Sovereign Linux Conformance

> **Document status:** Normative conformance architecture.
> **Primary profile:** `sovereign_linux_node`
> **Optional overlays:** `high_assurance`, `sovereign_offline`, `appliance_shell`, only when compatibility is declared.
> **Claim rule:** A sovereign Linux claim applies to one exact node, profile composition, environment, artifact set, and evidence set.

## 1. Purpose

This document defines how kOA proves conformance for the sovereign Linux node profile (`sovereign_linux_node`) and its compatible overlays.

The sovereign Linux node is the hardened Linux production profile with explicit identity, recovery, offline, privilege, and assurance controls.

Conformance verifies that a declared deployment:

- matches the exact profile composition;
- satisfies the minimum hardware envelope;
- boots and runs admitted system artifacts;
- preserves identity, privilege, component, tenant, and storage boundaries;
- maintains locally enforceable policy and resource governance;
- continues its declared sovereign core without Internet access;
- verifies backups and recovery;
- activates only compatible Release Sets;
- produces valid test evidence;
- degrades safely;
- can revoke its claim when material applicability changes.

This document defines the claim and evidence model. Profile contracts own exact profile values.

## 2. Scope

### 2.1 Included scope

This document applies to conformance claims for:

- one sovereign Linux node;
- the `sovereign_linux_node` primary profile;
- compatible `high_assurance` composition;
- compatible `sovereign_offline` composition;
- compatible `appliance_shell` composition;
- hardware and resource envelopes;
- system, service, governance, and knowledge releases;
- node identity and trust;
- privilege and break-glass behavior;
- storage, backup, restore, and recovery;
- network and disconnected operation;
- services, jobs, queues, and resources;
- component and integration boundaries;
- security and software supply chain;
- test evidence, exceptions, revocation, and claim retention.

### 2.2 Excluded claims

This document does not establish conformance for:

- `developer_linux_workstation`;
- `developer_windows_wsl`;
- `user_lightweight`;
- `build_farm`;
- `control_plane`;
- `sovereign_hub`;
- an undeclared overlay;
- a historical kOA Linux recipe;
- a Linux host merely running some kOA processes.

Those profiles require their own claims and matrices.

### 2.3 Sovereign Linux node and sovereign hub

The sovereign Linux node is a hardened production-node profile.

The sovereign hub is a separate multi-service sovereign deployment profile for shared or coordinated operation.

A hub can include Linux nodes, but hub conformance does not automatically prove every included node satisfies the sovereign Linux node profile, and node conformance does not automatically prove hub topology or scale conformance.

### 2.4 Profile and recipe separation

Recipes can describe implementation using:

- rootless Podman;
- Quadlet;
- systemd;
- a particular filesystem;
- a firewall implementation;
- a backup tool;
- a boot implementation;
- an appliance compositor.

A recipe becomes a conformance requirement only when the active profile or overlay contract adopts it.

## 4. Model and Responsibilities

### 4.1 Conformance layers

Sovereign Linux conformance has six layers:

| Layer | Question |
| --- | --- |
| Composition | Is the exact primary profile and overlay set valid? |
| Platform | Does hardware, booted system, storage, network, and recovery match the profile? |
| Runtime | Are services, resources, identities, policies, and boundaries operating correctly? |
| Lifecycle | Are artifacts, updates, rollback, forward repair, backup, and offline transfer controlled? |
| Evidence | Did every required test produce exact valid evidence? |
| Claim | Does the complete aggregate support the declared node and scope? |

Failure in one required layer prevents a full claim.

### 4.2 Claim lifecycle

The claim lifecycle is:

`text
candidate
→ evaluated
→ conformant
`

Alternative states are:

`text
nonconformant
blocked
expired
revoked
superseded
`

A conformant claim is not permanent.

### 4.3 Profile-composition matrix

| Composition | Conformance interpretation |
| --- | --- |
| `sovereign_linux_node` | Baseline sovereign Linux node claim |
| `sovereign_linux_node + high_assurance` | Baseline plus every high-assurance requirement |
| `sovereign_linux_node + sovereign_offline` | Baseline plus disconnected-operation and recovery requirements |
| `sovereign_linux_node + appliance_shell` | Baseline plus restricted appliance-shell requirements |
| Multiple overlays | Every pair and the complete set must declare compatibility; all additive requirements apply |
| Undeclared overlay | Claim blocked |
| Overlay inferred from behavior | Claim blocked |

### 4.4 Responsibility allocation

| Actor or component | Responsibility |
| --- | --- |
| Profile owner | Owns exact profile and overlay requirements |
| Node owner | Declares target node and requested claim |
| Conformance validator | Resolves the test matrix and evaluates evidence |
| Test executor | Runs admitted tests without owning the claim |
| Evidence registry | Stores immutable execution evidence |
| Traceability registry | Links profile requirements to tests and evidence |
| Identity and Trust | Resolves node, service, operator, tool, and trust identities |
| Governance Policy Runtime | Decides governed test actions, exceptions, and disclosures |
| Resource Governor | Constrains conformance workloads |
| Audit Broker | Provides selective access to required receipts and evidence |
| Release authority | Owns channel releases and Release Sets |
| Component owners | Own component test interfaces and authoritative data |

### 4.5 Test-matrix domains

The sovereign Linux test matrix contains at least:

1. profile composition;
2. hardware and capacity;
3. system and boot;
4. identity and credentials;
5. privilege and break-glass;
6. storage boundaries;
7. backup and restore;
8. network and time;
9. offline continuity;
10. services and component inclusion;
11. resource governance and scheduling;
12. governance, audit, and cultural rights;
13. component and integration boundaries;
14. AI boundary;
15. software supply chain;
16. release, update, rollback, and forward repair;
17. overlay-specific controls;
18. evidence completeness and claim revocation.

Exact test IDs remain owned by the test catalog.

### 4.6 Hardware evaluation

Hardware evidence combines:

- declared inventory;
- firmware or platform inventory where applicable;
- operating-system observation;
- storage topology;
- encryption state;
- recovery and backup target identity;
- resource stress and enforcement evidence.

A nominal product label does not replace measured evidence.

### 4.7 System and boot evaluation

System evaluation verifies:

- exact system-channel artifact;
- booted operating-system and kernel identity;
- integrity and signature behavior required by the profile;
- active and recovery system state;
- failed-verification behavior;
- update and prior-state retention;
- system provenance;
- required system services.

An immutable signed image is tested only when adopted by the profile.

### 4.8 Identity and privilege evaluation

Identity evaluation covers:

- node identity;
- device identity;
- service identities;
- operator identities;
- workload identities;
- tenant scope where applicable;
- certificates, tokens, and trust roots;
- rotation and revocation;
- emergency credentials.

Privilege evaluation proves that normal operation uses bounded identities and the narrow privileged path.

### 4.9 Storage and recovery evaluation

Storage evaluation distinguishes:

- authoritative component stores;
- replicas;
- projections, caches, and indexes;
- artifact storage;
- audit and evidence storage;
- backup and archive storage;
- temporary and repair storage.

Backup conformance requires a tested restore.

Possession of backup bytes without a validated owner-approved restore does not satisfy the requirement.

### 4.10 Network and offline evaluation

Network evaluation compares declared and observed:

- interfaces;
- addresses and zones;
- routes;
- inbound services;
- outbound destinations;
- peers;
- tunnels;
- name resolution;
- time sources;
- update and synchronization paths.

Offline evaluation verifies continued operation using locally admitted authority and artifacts, not merely cable disconnection.

### 4.11 Runtime evaluation

Runtime evaluation verifies:

- profile-included components;
- service identity and artifact identity;
- dependencies and interfaces;
- activation mode;
- readiness;
- resource envelope;
- storage owner;
- network exposure;
- degradation mode;
- recovery.

An implementation technology is tested only when the profile selects it.

### 4.12 Security and supply-chain evaluation

Security evaluation includes:

- least privilege;
- secret handling;
- component storage boundaries;
- selective audit;
- integration manifests;
- external AI boundaries;
- break-glass;
- source and dependency admission;
- clean builds;
- SBOM and provenance;
- artifact signatures and admission;
- key and artifact revocation.

### 4.13 Evidence and claim aggregation

The aggregate resolves every applicable profile requirement to:

`text
requirement
→ traceability
→ test
→ exact evidence
→ result
`

The aggregate exposes all missing, blocked, failing, expired, revoked, and exception-dependent items.

## 6. Procedures or State Transitions

### 6.1 Declare the target claim

### 6.2 Resolve the test matrix

1. load profile and overlay requirements;

3. resolve locks and decisions;
4. resolve active exceptions;
5. resolve traceability to test IDs;
6. apply registered applicability rules;
7. construct the complete required test matrix;
8. block evaluation when a required normative fact lacks a test or controlled manual procedure.

### 6.3 Collect platform evidence

1. authenticate the node and test executor;
2. measure hardware resources;
3. identify storage and encryption;
4. identify recovery and backup targets;
5. identify booted system artifacts;
6. identify network and time configuration;

1. resolve overlay-specific requirements;
2. verify composition compatibility;
3. run every additive test;
4. verify conflicts are absent;
5. register evidence separately from baseline evidence;

### 6.7 Evaluate the claim

1. validate every evidence object;
2. bind evidence to the exact node and composition;
3. evaluate freshness and invalidation;
4. evaluate exceptions and compensating controls;
5. classify every required item;

7. produce the aggregate outcome;

- every required item passes or has a valid registered not-applicable disposition;

- the target state has not changed;

- a relevant test changes;

## 8. Cross-Component Interactions

### 8.1 Profile contracts

Profile contracts provide exact expected values and composition.

This document never fills a missing profile value from customary Linux practice.

### 8.2 Identity and Trust

Identity and Trust resolves the node, operators, services, tests, artifacts, credentials, and trust roots used by evidence.

Unresolved identity blocks the affected claim.

### 8.3 Governance Policy Runtime

Governance Policy Runtime authorizes destructive, privileged, sensitive, disclosure-bearing, exception-dependent, and break-glass tests.

Policy authorization does not turn a failed test into a pass.

### 8.4 Resource Governor

Resource Governor constrains conformance jobs and supplies evidence of runtime resource enforcement.

Test capacity does not relax profile limits.

### 8.5 Audit Broker

Audit Broker supports selective access to test, decision, activation, and recovery evidence.

It does not become the canonical owner of profile or component state.

### 8.6 Component owners

Component owners define test interfaces, authoritative stores, readiness, degradation, migration, and recovery behavior.

Conformance tools do not receive general cross-component write authority.

### 8.7 Release authorities

Release authorities supply exact system, services, governance, knowledge, and Release Set identities.

A release signature is evidence of signed identity, not complete node conformance.

### 8.8 External integrations

Integration tests verify exact manifests, minimum data transfer, authentication, failure isolation, removal, and offline behavior.

An external integration is never required for the sovereign core unless the profile explicitly defines a non-core dependent capability.

## 9. Decision Closure and Prohibited Assumptions

The following decisions are closed:

- sovereign Linux node is a distinct primary profile;
- overlays are explicit and additive;
- the minimum hardware envelope is eight modern cores, 32 GiB RAM, one terabyte encrypted SSD, a recovery target, and a verified backup target;
- 64 GiB RAM is recommended rather than a baseline minimum;
- profile-specific Linux mechanisms do not become global requirements;
- rootless Podman and Quadlet are preferred sovereign Linux choices, not universal requirements;
- Kubernetes is not required for the sovereign Linux node;
- the sovereign core does not depend on Internet or external AI;
- all four release channels participate in Release Set compatibility;
- component data ownership remains enforced;
- backups require verified restore evidence;
- full conformance requires complete exact evidence;
- material changes revoke or supersede the claim.

Prohibited assumptions include:

- treating any Linux host as a sovereign Linux node;
- treating a developer workstation as production conformance;
- treating sovereign-hub conformance as node conformance;
- inferring an overlay from installed packages;
- making Secure Boot or TPM mandatory without profile adoption;
- making one distribution, filesystem, firewall, service manager, or container runtime mandatory from a recipe;
- requiring Kubernetes on the sovereign Linux node;
- treating an encrypted disk as complete storage-boundary conformance;
- treating backup creation as restore proof;
- treating process health as service readiness;
- treating network disconnection as `sovereign_offline`;
- treating external voice or AI availability as core conformance;
- treating valid signatures as full release or node conformance;
- using evidence from another node, profile version, architecture, or Release Set;
- hiding missing evidence behind an exception;
- representing partial conformance as full conformance.

## 11. Non-Normative Examples

### 11.1 Baseline sovereign Linux node

A node declares `sovereign_linux_node@1.0.0`.

Evidence proves eight cores, 32 GiB RAM, one terabyte encrypted SSD, a verified recovery target, a verified backup target, the exact active Release Set, component boundaries, offline core behavior, and complete baseline tests.

### 11.2 Recommended memory

A node has 32 GiB RAM and passes the active baseline contract.

The documentation recommends 64 GiB, but the validator does not fail the baseline claim unless an overlay or later profile version raises the minimum.

### 11.3 High-assurance composition

A node declares `sovereign_linux_node + high_assurance`.

Baseline evidence passes, but the high-assurance quorum test is missing. The complete composed claim is blocked; the validator does not represent it as high-assurance conformant.

### 11.4 Offline composition

A node is physically disconnected but cannot validate local policy bundles or restore from its local backup target.

It does not satisfy `sovereign_offline`, even though Internet access is absent.

### 11.5 Container recipe

A profile version adopts rootless Podman and Quadlet.

Conformance tests rootless execution, exact image identity, service definitions, capabilities, mounts, network boundaries, and recovery. Another profile version using a different declared runtime is evaluated against its own contract.

### 11.6 Appliance shell

A node uses a minimal Wayland compositor and an embedded web interface.

The `appliance_shell` claim still requires tests for restricted general-purpose behavior, escape controls, session boundaries, and recovery access. Absence of GNOME alone is insufficient.

### 11.7 Claim revocation

A conformant node activates a new services release outside the claimed Release Set.

The prior claim is revoked or superseded until the new exact Release Set and all affected evidence pass.
