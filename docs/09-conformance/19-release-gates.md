# Release Gates

## 1. Purpose

This document defines the kOA release-gate model.

A release gate is a versioned, evidence-backed conformance decision applied to one immutable candidate Release Set. Gates prevent incomplete authority, incompatible channel combinations, missing tests, stale evidence, unsafe component boundaries, invalid profile claims, weak recovery posture, or open operational risk from entering active authority.

A release is not a collection of individually acceptable artifacts. It is one compatible Release Set containing exactly four channel versions:

```text
system
services
governance
knowledge
```

The release-gate model verifies the complete set, its claimed profiles, its artifacts, its operational readiness, and its activation path.

Final approval does not activate the Release Set. Activation remains a separate privileged lifecycle transaction.

## 2. Scope

This document applies globally to:

- candidate Release Sets;
- system, services, governance, and knowledge channels;
- release manifests;
- artifact signatures and integrity;
- compatibility;
- canonical authority;
- documentation;
- decisions and locks;
- profiles and overlays;
- component contracts;
- migrations;
- integrations;
- AI boundaries;
- tests;
- evidence;
- service-level objectives;
- incidents;
- backup and disaster recovery;
- offline continuity;
- profile claims;
- AI-context packages;
- exceptions;
- approvals;
- activation;
- post-activation validation;
- rollback, forward repair, invalidation, supersession, and revocation.

This document does not define the contents of each test, component contract, profile, artifact class, SLO, recovery plan, or activation adapter. Their canonical owners define those facts.

## 4. Gate Model and Decision States

### 4.1 Gate classes

The mandatory gate classes are:

```text
canonical_authority
documentation
component_contracts
profiles
artifacts
release_set_compatibility
security
ai_boundary
tests
evidence
operations
disaster_recovery
migration
offline
integrations
profile_claims
ai_context
activation_readiness
```

A release policy can add narrower gates. It cannot omit a mandatory applicable class.

### 4.2 Gate identity

A gate record contains:

```text
gate_id
gate_version
gate_class
release_set_ref
profile_refs
scope
dependencies
executed_checks
result
reason_codes
exception_refs
approval_refs
test_refs
evidence_refs
started_at
finished_at
valid_until
invalidation_triggers
receipt_ref
```

A gate result belongs to one candidate Release Set and one evaluated scope.

### 4.3 Gate results

Gate results are:

| Result | Meaning |
| --- | --- |
| `pass` | Every applicable check executed successfully |
| `fail` | One or more applicable checks produced a definite failure |
| `blocked` | Required authority, tool, environment, source, or evidence was unavailable |
| `waived_by_approved_exception` | A valid bounded exception covers the failed or unavailable obligation |
| `expired` | The validity interval ended |
| `invalidated` | A bound input changed or a trigger made prior evidence unreliable |
| `not_applicable` | A canonical rule excludes the gate for the evaluated scope |

`not_applicable` is rare for mandatory global gates and requires a canonical applicability rule.

### 4.4 Release decisions

Release decisions are:

```text
approved
approved_with_exceptions
rejected
blocked
expired
invalidated
superseded
revoked
```

A release decision is separate from Release Set lifecycle state and activation state.

### 4.5 Gate dependency order

The default dependency order is:

```text
canonical authority
documentation and generated content
component contracts
profiles
artifacts
Release Set compatibility
security and AI boundaries
tests
evidence
operations
disaster recovery
migration
offline behavior
integrations
profile claims
AI context
activation readiness
final release decision
```

Independent checks can run in parallel when they do not rely on incomplete inputs. Final evaluation respects the dependency graph.

### 4.6 Immutable evaluated subject

After gate execution begins, a material change to the candidate creates a new Release Set version or candidate identity.

The evaluated subject includes:

- all four channel versions;
- channel manifests;
- artifact identities;
- artifact content and signatures;
- profile set;
- component contracts;
- migrations;
- integration configuration;
- release policy;
- gate policy.

A local rebuild that changes a functional artifact creates a different evaluated subject.

## 6. Mandatory Gate Procedures

### 6.1 Canonical-authority gate

This gate verifies:

- active authority registry;
- valid active registries and schemas;
- accepted decisions;
- decision closure;
- unique canonical ownership;
- no duplicate active facts;
- lock closure;
- requirement references;
- ADR status;
- exception status;
- prohibited open-state marker absence.

Failure blocks every dependent gate.

### 6.2 Documentation gate

This gate verifies:

- required active documents;
- metadata;
- English language;
- canonical references;
- generated requirement blocks;
- generated-content reproducibility;
- no duplicate active documents;
- no manual generated drift;
- validation command success;
- documentation release completeness.

Ordinary Markdown file-content hashes are not required.

### 6.3 Component-contract gate

This gate verifies for every required or active component:

- identity;
- purpose;
- responsibilities;
- authority boundary;
- data ownership;
- interfaces;
- events;
- states;
- failure behavior;
- idempotency;
- security;
- privilege;
- resources;
- offline behavior;
- recovery;
- tests and evidence.

Direct cross-component authoritative-store writes fail the gate.

### 6.4 Profile gate

This gate evaluates every claimed effective profile:

```text
global baseline
+ exactly one primary profile
+ compatible overlays
+ approved bounded exceptions
```

It verifies:

- profile versions;
- overlay compatibility;
- required and prohibited components;
- hardware and resource envelope;
- security boundary;
- networking;
- integrations;
- offline behavior;
- recovery;
- non-claims.

Development-profile success cannot establish production or sovereign profile readiness.

### 6.5 Artifact gate

For every artifact, this gate verifies:

- artifact identity and class;
- canonical owner;
- immutable version;
- manifest;
- schema;
- provenance;
- functional integrity where required;
- signature and signer trust where required;
- release-channel membership;
- target profiles;
- compatibility;
- revocation;
- rollback or recovery behavior.

### 6.6 Release Set compatibility gate

This gate verifies exactly one version of each channel:

```text
system
services
governance
knowledge
```

It validates directional compatibility for:

- publication;
- assembly;
- staging;
- activation;
- rollback;
- forward repair;
- every claimed profile.

No individual channel approval substitutes for this result.

### 6.7 Security and AI-boundary gates

Security validation covers:

- identity and trust;
- authorization;
- privileged broker;
- secrets;
- protected data;
- audit durability;
- private proof access;
- network boundaries;
- integration boundaries;
- recovery security.

AI-boundary validation covers:

- no native AI authority;
- approved external surfaces only;
- controlled export and reimport;
- provenance;
- local validation;
- human acceptance;
- optional isolated non-authoritative SenTient;
- no direct authoritative AI writes.

### 6.8 Test gate

The test gate resolves required tests from:

- requirements;
- profiles;
- components;
- artifacts;
- migrations;
- integrations;
- security;
- offline behavior;
- recovery;
- release policy.

It verifies actual execution against the candidate Release Set.

Cached evidence is usable only when its validity and equivalence rules cover the current candidate.

### 6.9 Evidence gate

Evidence validation confirms:

- subject binding;
- candidate Release Set binding;
- profile binding;
- environment;
- source or implementation version;
- test identity;
- producer;
- time;
- result;
- integrity or authenticity where required;
- validity;
- traceability.

Missing required evidence blocks release approval.

### 6.10 Operations gate

The operations gate evaluates:

- applicable SLO states;
- measurement quality;
- error-budget status;
- incidents;
- capacity and resource reserves;
- audit and receipt delivery;
- backup status;
- operational runbooks;
- rollback readiness;
- monitoring and alerting;
- degraded-mode communication.

A passing SLO does not erase an active severe security or recovery issue.

### 6.11 Disaster-recovery gate

This gate verifies:

- current backup manifests;
- restore or reconstruction tests;
- recovery objectives;
- complete Release Set recovery;
- recovery environment;
- replacement-node process;
- identity and trust recovery;
- dual-authority prevention;
- offline recovery;
- findings and remediation.

A backup without verified restore evidence does not pass.

### 6.12 Migration gate

Migration validation covers:

- source and target schemas;
- owning component;
- expected state;
- rehearsal;
- compatibility;
- rollback classification;
- forward-repair path;
- data integrity;
- audit preservation;
- pending workflows;
- recovery evidence.

A forward-only migration requires a current forward-repair path.

### 6.13 Offline gate

For offline-capable claims, this gate validates:

- disconnected startup;
- local identity and policy;
- local audit;
- deferred queue durability;
- signed transfer bundles;
- quarantine;
- replay and downgrade prevention;
- local complete Release Set activation;
- rollback;
- disaster recovery;
- reconnection reconciliation.

Connected-only evidence does not pass the offline gate.

### 6.14 Integration gate

This gate verifies every enabled integration:

- registry entry;
- endpoint;
- authentication;
- authorization;
- data classification;
- purpose;
- minimum data;
- destination;
- retry and timeout;
- idempotency;
- provenance;
- offline behavior;
- removal;
- local acceptance;
- secret handling.

Disabled optional integrations remain covered by local behavior tests.

### 6.15 Profile-claim gate

Every release compatibility, deployment, or operational claim verifies:

- exact effective profile;
- complete Release Set;
- requirement dispositions;
- tests;
- evidence;
- exceptions;
- non-claims;
- validity;
- invalidation triggers.

### 6.16 AI-context gate

This gate verifies:

- package registration;
- exact source and authority versions;
- scope and excluded scope;
- profile composition;
- component boundaries;
- trust classes;
- secret exclusion;
- deterministic generation;
- clean regeneration;
- freshness;
- executed validation.

## 7. Exceptions, Approvals, and Final Decision

### 7.1 Exception admission

A gate exception record identifies:

```text
exception_id
gate_ref
requirement_refs
release_set_ref
profile_refs
scope
owner
approving_authority
effective_at
expires_at
reason
compensating_controls
test_refs
evidence_refs
release_impact
exit_criteria
revocation_conditions
```

An exception cannot silently transform a failing gate into `pass`.

### 7.2 Non-waivable conditions

The following conditions remain non-waivable:

- incomplete four-channel Release Set;
- invalid authority registry;
- missing owner decision for a semantic change;
- active canonical conflict;
- invalid or unverifiable release signature;
- secret-value exposure;
- direct unauthorized cross-component write;
- missing critical audit durability;
- absent rollback, forward-repair, or recovery for a required transition;
- fabricated test or validation result;
- unknown activated artifact identity;
- blind replay of an unknown privileged or migration effect.

### 7.3 Approval roles

Applicable approval roles can include:

- release owner;
- governance owner;
- security reviewer;
- profile owner;
- component owner;
- migration owner;
- operations owner;
- recovery owner;
- evidence reviewer;
- final release authority.

Separation of duties is required where policy or risk class demands it.

### 7.4 Final decision procedure

Final decision verifies:

1. the candidate identity remains unchanged;
2. mandatory gates are current;
3. every result is pass or validly waived;
4. every waiver is visible and current;
5. approvals are complete;
6. signature and signer trust verify;
7. activation prerequisites pass;
8. rollback or forward repair remains ready;
9. evidence and receipts are durable;
10. no invalidation trigger has fired.

The decision is `approved_with_exceptions` when any gate is validly waived.

### 7.5 Decision receipt

The decision receipt identifies:

- Release Set;
- gate results;
- exceptions;
- approvals;
- authority;
- decision;
- reason codes;
- issue and expiry time;
- activation prerequisites;
- rollback or repair references;
- evidence;
- invalidation triggers.

The receipt is immutable.

## 8. Activation Readiness and Post-Activation Control

### 8.1 Activation-readiness gate

This gate verifies:

- target node or scope identity;
- target profile;
- expected active Release Set;
- candidate Release Set;
- staged artifacts;
- compatibility;
- trust;
- resource admission;
- migration readiness;
- rollback target;
- forward-repair path;
- recovery environment;
- receipt storage;
- privileged broker readiness.

### 8.2 Activation transaction

Activation:

1. binds request and idempotency identity;
2. verifies expected state;
3. stages dependent artifacts;
4. commits dependent state;
5. commits the authority pointer last;
6. verifies actual state;
7. records the activation receipt;
8. starts post-activation validation.

The final release decision does not bypass any activation check.

### 8.3 Post-activation validation

Post-activation checks include:

- active Release Set identity;
- four active channel versions;
- profile state;
- component readiness;
- critical capability results;
- migration state;
- audit and receipts;
- SLO measurement;
- integrations;
- privilege boundaries;
- offline promises;
- backup and recovery posture;
- profile claims.

### 8.4 Post-activation outcomes

Outcomes are:

```text
validated_active
active_degraded
rollback_required
forward_repair_required
recovery_required
quarantined
```

`active_degraded` requires an explicit allowed degraded state and does not conceal failed mandatory safety checks.

### 8.5 Rollback

Rollback selects a complete prior compatible Release Set.

It uses the same identity, authorization, expected-state, compatibility, migration, evidence, privilege, and receipt controls as activation.

### 8.6 Forward repair

Forward repair creates a new immutable Release Set candidate and repeats applicable release gates.

It does not modify the failed Release Set in place.

### 8.7 Claim invalidation

Activation or recovery invalidates claims bound to a different Release Set or state.

New or renewed profile claims require current post-activation evidence.

## 9. Invalidation, Failure, and Historical Integrity

### 9.1 Invalidation triggers

Gate invalidation triggers include:

- authority change;
- decision change;
- requirement or lock change;
- profile change;
- component-contract change;
- artifact or manifest change;
- signature or trust change;
- revocation;
- migration change;
- integration change;
- configuration drift;
- test failure;
- evidence expiry;
- incident impact;
- SLO or measurement impact;
- backup or recovery failure;
- exception expiry;
- candidate rebuild;
- activation result.

The gate record declares which triggers apply.

### 9.2 Failure model

| Failure | Required treatment |
| --- | --- |
| Candidate Release Set incomplete | Reject. |
| Authority or registry invalid | Block all dependent gates. |
| Decision closure missing | Block semantic release approval. |
| Profile composition invalid | Fail profile and dependent gates. |
| Artifact signature invalid | Fail and quarantine. |
| Compatibility unknown | Block. |
| Required test not executed | Block or fail according to policy. |
| Evidence stale or mismatched | Block evidence and dependent gates. |
| Critical incident active | Apply the operations policy and block when required. |
| Backup restore evidence expired | Fail disaster-recovery readiness. |
| Migration outcome unknown | Block activation and enter reconciliation. |
| Offline evidence absent | Fail the offline claim. |
| Exception expired | Reevaluate the affected gate without the waiver. |
| Gate receipt storage unavailable | Block final decision. |
| Candidate changed after evaluation | Invalidate affected gates. |
| Post-activation check fails | Roll back, repair, quarantine, or recover. |
| Release authority unavailable | Preserve evaluated state and block approval. |

### 9.3 Historical preservation

Gate records, release decisions, activation receipts, rollback receipts, failures, exceptions, invalidations, and revocations remain immutable.

Corrections create linked records.

A superseded result is not deleted or presented as current.

### 9.4 Public and restricted evidence

A public release receipt can expose:

- Release Set identity;
- channel versions;
- decision;
- issue time;
- exception presence;
- activation status;
- verification state;
- public recourse reference.

Detailed vulnerabilities, private proofs, security configuration, secret references, and protected incident evidence remain restricted.

2. exactly four channel versions are present;

10. artifacts, signatures, provenance, and release-channel membership pass;
11. complete Release Set compatibility passes;

14. evidence is attributable, current, and bound to the candidate;
15. operations, SLOs, incidents, capacity, and receipt durability pass;
16. disaster recovery and executable restore evidence pass;

## 11. Non-Normative Examples

### 11.1 Complete candidate

A candidate contains system 1.4.0, services 2.3.1, governance 3.2.0, and knowledge 5.1.0. All gates evaluate that exact set rather than four independent channel candidates.

### 11.2 Missing test

A required offline rollback test is listed but did not execute. The test gate is blocked, so the Release Set cannot receive final approval for the sovereign-offline claim.

### 11.3 Valid exception

One noncritical reporting feature has a bounded approved exception with compensating monitoring, current tests, expiry, and exit criteria. The affected gate is `waived_by_approved_exception`, and the release decision is `approved_with_exceptions`.

### 11.4 Non-waivable failure

The Release Set signature cannot be verified. No exception can waive this condition, and the candidate is rejected.

### 11.5 Evidence mismatch

A component test passed on an earlier source revision. No validated equivalence exists, so the evidence gate rejects reuse for the current candidate.

### 11.6 Development profile

A Windows WSL candidate passes developer-profile gates. It still cannot support production, sovereign, high-assurance, release-signing, or control-plane claims.

### 11.7 Migration repair

A forward-only migration has no safe rollback. The migration gate passes only after a tested forward-repair Release Set and recovery path are current.

### 11.8 Post-activation failure

Activation commits, but a critical receipt-durability check fails. Post-activation validation triggers rollback or recovery while preserving the original release decision and activation receipt.

### 11.9 Candidate change

A services artifact is rebuilt after gate completion. The Release Set identity changes, and every affected gate becomes invalidated.

### 11.10 Public release receipt

A public receipt shows the Release Set, four channel versions, approval result, exception presence, activation state, and recourse reference. Restricted gate evidence remains protected.
